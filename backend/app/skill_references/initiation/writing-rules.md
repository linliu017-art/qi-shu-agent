# 写法规则

## 一、证据分级

报告和卡片里每一个数字、每一句用户的话、每一条竞品信息，都要带一个等级标签：

| 标签 | 含义 | 能支撑什么 |
|---|---|---|
| `实测` | 埋点、日志、实验、对照测试得到的数据 | 可作现状基线和验收依据 |
| `原话` | 真实用户的访谈或反馈原文（注明谁、何时） | 可支撑需求成立 |
| `业务方表达` | 业务方、提需方的判断和描述 | 只能作为线索，需要核实 |
| `测算` | 基于假设推算的收益、工时、规模 | 不能当结果写；必须写口径和来源 |
| `假设` | 尚未验证的判断 | 必须列入待验证，写验证方式 |
| `模拟` | AI 生成或角色扮演的样本 | 只能用来设计调研提纲，不算证据 |

外部信息额外写出处和获取日期。

**相关 ≠ 因果**：两组数据有差异，但分组、时间、规模等因素没控制时，只能写"相关信号，值得验证"，并写出试点里用什么方式验证。

**目标值的写法**：
- 有现状基线的：写"现状 → 目标"，目标优先对齐竞品当前的实际水平，保证够得着。
- 没有基线的（功能未上线、缺埋点）：只定方向，写"随开发预埋，上线后建立基线"，不做精确预测。
- 收入、转化这类结果指标，没有历史数据支撑时不给具体数字，写清由谁、在什么时间点之后再定。

## 二、写作风格

- **结论先行**：每一节第一句就是这一节的结论。只读每节第一句，应能拼出整份报告的逻辑。
- **大白话**：写读者一听就懂的话。用"用户找不到这个功能"，不用"功能可发现性不足"。
- **每条判断配证据**：一个数字或一句原话，并标等级。
- **一句话逻辑**：报告开头用一句话讲清"问题 → 原因 → 我们做什么"的因果链。
- **说清分工和不做什么**：跨团队读者最关心谁承接、占不占自己的人力、哪些不做。
- **承认缺口**：说不清的地方直接写"目前说不清"，并写怎么补。

禁用：赋能、抓手、闭环打通、深度融合、全面升级、行业领先、颠覆、打造生态等空话；没有数字支撑的"显著提升""大幅降低"。

## 三、好坏对照（抽象模式）

| 环节 | ❌ 坏写法 | ✅ 好写法 |
|---|---|---|
| 问题定义 | 做一个 AI 助手，提升用户效率 | <某类人>在<某场景>下<卡在某一步>，现在只能<怎么凑合>，代价是<多少时间或钱> |
| 用户画像 | 25–35 岁，一线城市，本科以上 | 他知道什么、在乎什么、什么时候用、因为什么卡住，附一句原话 |
| 调研结论 | 用户普遍认为很需要 | <几>个受访者中<几>个做过<某件事>，原话"……" |
| 竞品结论 | 竞品功能更丰富 | 竞品在<某能力>上有<具体差距>，用户评价里<多少比例>提到<什么> |
| 差异化 | 我们体验更好、技术更强 | 盯 X 用户，他最在乎 Y，竞品做不了，因为 Z |
| 优先级 | 以下 30 项均为 P0 | 一个假设；必须做 N 项，每项连回痛点；明确不做 M 项，每项有理由 |
| 收益 | 预计带来 xxx 万收益 | xxx 万为<谁>的测算，口径<……>，未经复核；试点用<指标>验证 |
| AI 能力 | AI 智能识别并自动处理 | AI 做<什么>，做到<指标 ≥ 阈值>，没把握时<转人工 / 让用户确认> |
| 风险 | 存在一定技术风险 | <具体风险>；触发条件<……>；降级方案<……>；负责人<……> |
| 停止条件 | （不写） | 第<几>周<指标>未达<阈值>，停止 / 转向 <方案> |

## 四、交付前自查

- [ ] 一页纸结论能独立看懂：做不做、为谁、先做什么、怎么证明、投多少、什么时候停
- [ ] 问题定义里没有功能名
- [ ] 每个数字都有等级标签和来源
- [ ] 没有把测算当结果、把相关当因果
- [ ] 明确不做的每一项都有理由
- [ ] AI 专项四问都有回答
- [ ] 每个阶段都有"不过闸怎么办"
- [ ] 决策待办都有责任人和时间
- [ ] 没有禁用词

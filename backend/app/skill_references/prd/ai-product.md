# AI 产品专项

仅对实际涉及的能力展开。不要从报告生成案例推导出所有产品都要采用多 Agent、RAG 或固定编排。

## 能力与执行约定

每项能力写清职责、输入、资料与工具、执行约束、输出结构、质量标准、人工参与点和失败处理。

若任务确需拆分，可采用规划/生成/审计/优化等职责，但解释拆分依据和传递关系；简单能力无需强行拆 Agent。明确什么情况下进入下一步、回退或停止，以及部分成功如何处理。

工具约定包括用途、输入输出、调用条件、资料与权限范围及失败行为。产品 PRD 定义可见行为和必要约束，工程规格再决定具体接口与部署。

## 上下文与一致性

按需区分：

| 信息 | 要定义的约定 |
|---|---|
| 全局配置 | 目标、领域、格式、风格等，由谁设置及生效范围 |
| 已确认事实 | 来源、人工确认状态、版本及冲突处理 |
| 历史记忆 | 已完成任务摘要、术语、衔接信息及更新规则 |
| 当前参考资料 | 检索片段或用户材料、适用任务及有效期 |
| 运行结果 | 状态、审计问题、重试信息、后续环节消费方式 |

说明哪些环节可读写、何时更新、失败能否恢复及用户修改后的失效范围。缓存可以避免重复检索，但要考虑资料变化。输出格式在影响跨环节传递时提供必要字段与约束，不为展示技术深度而堆砌 JSON。

## 事实与溯源

- 将用户确认或可信资料支撑的项目事实与模型推断分开。生成内容不可自动升级为已确认事实。
- 对关键事实给出可核查来源；引用展示按资料形态提供文档、位置或链接，不假定所有资料都有页码。
- 资料缺失、过期或冲突时说明提示、补充输入、确认或停止规则。引用是否存在、是否支持结论与事实是否正确分别评估。
- 审计可按严重度、问题类型、位置、错误片段、事实依据、原因及修复建议输出。优化不得无依据改写已确认事实；关键修改保留审阅或确认方式。
- 如允许通用知识补充，说明许可范围、用户知情/确认方式及输出标记，避免与有依据的项目事实混淆。

## 提示词作为版本化附件

提示词保留角色、输入变量、行动路径、工具规则、输出规范等有用结构，并与模型、工具和资料配置关联版本。核心行为与验收标准留在 PRD 正文，不能只藏在提示词里。不要在提示词中硬编码未经确认的项目事实或把角色资历描述当成质量保证。

## 人工控制与产品体验

明确用户何时确认输入、计划或关键事实，何时能修改、停止、重试、接受或撤销结果。长任务区分已完成与处理中，说明保存和恢复粒度。只有需要人判断的点才安排确认，不在所有步骤增加弹窗。

## AI 评测与回归

真实任务覆盖有资料、缺资料、资料冲突及专业边界等相关情形，同时评估单环节与最终成果。按实际能力选择事实正确性、完整性、任务达成、引用支持、结构、风格、一致性、耗时、成本等维度。

- 业务专家/用户提供任务、依据和红线，产品与技术维护可执行用例与结果分析。
- 对关键事实、权限或业务风险设置单独红线，不以平均得分抵消。
- 明确样本代表性、评分人/规则、重复次数与通过条件。小规模用例通过不等于已证明广泛可靠。
- 模型、提示词、工具、资料或编排变化后，执行覆盖影响范围的回归；高耦合或高风险链路执行完整核心回归。
- 故障归因区分资料、检索、生成、审计、优化与交互，反馈要能定位环节。
- 线上采纳率和修改幅度按任务定义，导出不自动等于采纳；与人工质量抽检结合。
